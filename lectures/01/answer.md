## 宿題

- 取り組んだレベル：実装
- やったこと：
  - `app/ask.py` に `--chat` オプションを追加した（`uv run python -m app.ask --chat`）。
  - `client.chats.create(model=MODEL)` で会話セッションを作り、入力ループで `chat.send_message()` を呼ぶ。chats オブジェクトがそれまでのやり取りを履歴として保持し、毎回まとめてモデルに送る。
  - 空行・`exit`・Ctrl-D で終了。API エラー（429 など）はメッセージを表示して会話を継続する。
  - 各ターンで入力／出力トークン数と、implicit cache にヒットしたトークン数（`cached_content_token_count`）を表示する（演習で作った表示処理を `print_usage()` に切り出して共用）。
  - 引数なし／質問を渡す既存の1回呼び出しの動作は変えていない。
- 結果：
  - 1ターン目「私の名前は太郎です。一言で返事してください。」→「こんにちは、太郎さん！」（入力 14 / 出力 5）
  - 2ターン目「私の名前は何でしたか？一言で答えてください。」→「太郎。」（入力 34 / 出力 2）
  - 2ターン目で1ターン目の内容を踏まえて答えられた。
- 気づき・疑問：
  - 2ターン目の入力トークン数（34）は、2ターン目の質問だけでなく1ターン目の質問と応答を含んだ数になっている。会話履歴は「モデルが覚えている」のではなく、毎回クライアント側から履歴を丸ごと送り直しているため、会話が長くなるほど入力トークンが増えていく。
  - 毎回同じ前半部分（履歴）を送り直すなら、その部分の処理を使い回せるはずだと考え、Gemini API の implicit cache（2.5 以降のモデルで既定で有効。前半部分が一致するリクエストを自動でキャッシュする）の挙動を `gemini-3.5-flash-lite` で確かめた。

    | 実験 | 入力トークン | cached |
    |---|---|---|
    | 短い会話（上と同じ `--chat` の2ターンを再実行） | 14 → 36 | None, None |
    | 用語集（`data/glossary.json`）＋毎回違う質問を、履歴なしで4回連続送信 | 約 7,820 | 1回目 None、2〜4回目 4,079 |
    | 同じ内容を続けてもう一度4回 | 約 7,820 | 4回とも 4,079 |
    | chats で1ターン目に用語集を渡し、短い質問を3回続ける | 7,819 → 7,934 | 4,079 → 4,073 → 4,067 → 4,061 |

    - 短い会話ではキャッシュは効かなかった。公式ドキュメントには最小トークン数（Flash 系で 2,048〜4,096）があり、数十トークンの会話はそれを大きく下回る。flash-lite の最小値はドキュメントに記載がなかった。
    - 長い前半部分が共通なら、会話でなくても（履歴なしの別リクエストでも）ヒットした。chats の1ターン目も、直前の実験と前半部分が同じだったためか、初回からヒットした。
    - `prompt_token_count` は約 7,820 のまま変わらないので、cached は入力トークンの内数として数えられている。
    - 入力約 7,800 トークンのうち、ヒットしたのは常に約 4,079 トークンだった。全体がキャッシュされるのではなく、一定の大きさの単位で前半だけがヒットしているように見える。
    - 応答時間（1.1〜1.9秒）には、ヒットの有無で目立った差はなかった。
- 疑問：
  - chats で会話が進むと、cached が 4,079 → 4,073 → 4,067 → 4,061 と6トークンずつ減った。履歴の組み立て方で前半部分の区切りがずれているのかもしれないが、確かめられていない。
